# 찬양 DB·주보 저장본 실시간 연동

2026-10-18. `mindex.content-live.js`가 기존 department Broadcast 채널의
`content-committed` 이벤트를 공유한다. 메시지는 프로젝트·종류·레코드 ID와
중복 제거용 ID뿐이며 가사, 음원, 주보 본문을 전송하지 않는다.
같은 브라우저는 BroadcastChannel/storage, 다른 기기는 Supabase Broadcast를 쓴다.
운영 DB 스키마·권한 변경은 없다.

- 찬양 생성/저장/삭제와 주보·공통 양식의 성공한 저장 뒤에만 알린다.
  예배 편집에서 생성한 빈 곡도 포함한다. 실패한 CAS 저장은 알리지 않는다.
- 수신은 읽기 전용이다. 찬양은 곡·버전·가사·관련 곡을 별도 객체로 읽어
  모두 준비된 뒤 적용한다. 기존 사용자 버전 이름, 폼, 음원·타이밍 메타데이터를
  현재 정규화 경로로 보존한다. 기존 찬양 저장 자체는 여전히 여러 요청이며
  이 기능이 DB 트랜잭션을 추가하지는 않는다.
- 입력 포커스, 미저장 수정, 저장/로딩, 모달, 송출 창, 음악·영상 재생 중에는
  보류한다. 비동기 조회 후에도 편집 revision/선택/프로젝트/클라이언트와
  초안 fingerprint를 다시 비교한다. 찬양은 찬양 화면에서만 적용하여 예배의
  연결 가사나 진행 중인 슬라이드를 다시 생성하지 않는다.
- 선택한 곡/버전과 편집 화면 스크롤을 유지한다. 삭제된 선택 곡은 현재 화면을
  유지하고 알린다. 다른 곡의 추가·수정·삭제는 목록에 반영한다.
- 주보는 미저장 내용, 드래그, 양식/내용 모드, 인쇄 준비와 `afterprint`까지의
  인쇄 세션을 보호한다. 저장 revision이 달라진 경우에만 detached snapshot을
  적용하며 스크롤을 복원한다. 저장된 source snapshot과 명시적 빈 필드는
  기존 계약을 따른다. 조회 실패/원격 삭제는 현재 화면을 지우지 않는다.
- 공통 양식 편집 화면에서만 해당 양식 변경을 반영한다. 이미 저장한 주보에
  새 공통 양식을 자동으로 덮어씌우지 않는다.
- 재연결·온라인 복귀·창 복귀와 60초 간격으로 **현재 보이는 레코드**를 대조한다.
  전체 찬양 가사/음원 파일을 주기적으로 다운로드하지 않는다. 알림이 유실된
  비활성 레코드는 해당 레코드를 볼 때의 대조로 복구한다. 음원 자체는 이
  연동으로 재생하거나 다운로드하지 않는다.

검증: `tests/smoke_content_live.py`는 격리된 Chromium/WebKit 프로필에서
실제 수신/적용 경로, 버전·가사, 무변경 수신, 초안·포커스·재생 보호,
조회 중 입력, 재연결 복구, 주보 스크롤/인쇄 세션, 저장 성공/실패 알림을 검증한다.
인쇄 API만 모의 처리하며 시스템 인쇄창이나 fullscreen을 열지 않는다.
기존 주보 계약/편집 테스트와 예배 실시간 연동도 회귀 검증한다.

## 예배 공통 설정·참고자료 · 2026-10-18

같은 content-committed 채널에 service-settings / references 무효화를 추가한다.
예배 종류의 DB 메타데이터·고정 기본 항목과 참고자료의 링크·그룹·순서·활성 여부를
전체 페이지로 읽되, 소량의 설정 데이터만 조회한다. 예배 구조의 코드 기본값은
배포 대상이며 별도 DB 편집 기능을 새로 만든 것은 아니다.

실제로 성공한 종류별 저장 및 링크 생성/수정/삭제 뒤에만 알린다. 여러 종류 중
일부만 저장되어도 성공한 부분은 알림을 보낸다. 기존 저장 방식의 동시 수정 충돌
해결 정책은 바꾸지 않으며, 여러 사용자가 같은 필드를 저장하면 마지막 저장이 남을 수 있다.

수신측은 읽기 전용이다. 비활성 화면·미저장 초안·입력 포커스·모달·재생·송출·저장 중은
보류한다. 참고자료 편집기가 열려 있으면 삭제도 편집 완료 후 반영한다. 예배 종류는
열린 예배/송출/주보 문서가 있으면 보류하여 기본 항목 projection을 바꾸지 않는다.
기존 예배 본문·폼·가사·atomic baseline은 갱신하거나 저장하지 않는다.

조회 후 프로젝트/client/편집 revision/화면 선택/원본 설정 값을 재확인한다.
완전한 조회 실패나 불완전한 응답을 삭제로 처리하지 않는다. 변경이 없으면 DOM을
갱신하지 않고, 변경 시에도 스크롤과 선택을 유지한다. 새 socket/timer는 추가하지
않으며 기존 60초 복구·재연결·창 복귀를 공유한다. 숨김/보호 상태는 조회도 보류하고
알림은 종류별로 합쳐 중복 요청을 줄인다. 설정과 참고자료의 신호 누락 복구는 해당
화면이 안전할 때 수행한다.

검증: tests/smoke_shared_settings_live.py (Chromium/WebKit). 그룹/링크 변경·삭제,
초안/포커스/편집기/송출/조회 중 변경 보호, 스크롤, 무변경 DOM 유지, 재연결,
조회 실패와 저장 성공/실패 알림을 검사한다. 실제 기기 성능이나 동시 저장 충돌이
모두 해결됐다는 의미는 아니다.

## 저장한 말씀 자료 · 2026-10-18

`scripture` 알림은 성공한 saveScripture 응답 뒤에만 발행하며 기존 단일
Broadcast/복구 타이머를 공유한다. 생성·삭제 UI는 새로 추가하지 않는다.
말씀 화면에서 활성 mindex_scriptures 전체 페이지를 detached read하여 자료의
추가·수정·삭제/비활성화를 대조한다. 이 작은 저장 자료 테이블에는 revision
컬럼이 없으므로 현재 60초 복구에서도 자료를 읽는다. 성경 역본 본문 테이블,
장별 캐시, 전체 성경 corpus는 읽거나 변경하지 않는다. 외부 SQL 수정은
알림 발행자가 없으므로 다음 안전한 복구 조회에서 발견한다.

초안 fingerprint, 포커스, 모달, 송출·재생, 로딩·저장 중에는 조회/적용을
보류한다. 응답 후 client/project, 편집 revision, 선택 장절·역본·검색,
자료 배열/내용을 다시 확인한다. 잘못된 응답이나 페이지 실패를 삭제로
처리하지 않는다. 삭제된 현재 자료는 화면을 유지하고 안내하며, 선택을
떠난 후 대조에서 제거한다. 현재 자료 변경 때만 상세 화면을 다시 그리고
스크롤을 복원한다. 성경 읽기·검색 DOM과 장절 선택은 그대로 유지한다.
사용자 예배 본문과 주보 snapshot은 자동으로 다시 쓰지 않는다.

동일 자료 알림은 전체 자료 단위로 합치며 내용이 같으면 DOM을 갱신하지
않는다. 현재 저장 경로의 동시 편집 last-write 정책은 바꾸지 않는다.
검증: tests/smoke_scripture_live.py의 Chromium/WebKit 읽기 전용 수신,
저장 성공/실패 알림, 추가·삭제·비활성화, 1002행 페이지, 100개 알림 합치기,
초안·포커스·재생·조회 중 변경 보호, 스크롤/장절 보존, 오류·재연결 복구.


## 안전한 반영 대기 단축 · 2026-10-19

app.js의 createLiveRefreshScheduler를 교회력·예배·content 알림이 공유한다.
알림 묶음 대기는 200ms에서 80ms로 줄인다. 첫 예약을 뒤로 미루지 않아
연속 알림도 한 번에 처리한다. 입력 포커스 해제, media pause/ended, dialog
close에서는 기존 2초 보류 타이머보다 이른 예약으로 교체한다. 모든 기존
조회 전후 초안·송출·재생 guard는 유지한다. 미디어 이벤트 자체가 안전 판정을
대신하지 않는다. 대기 항목이 없으면 이벤트가 조회나 타이머를 만들지 않는다.

실패한 조회의 15초 backoff는 새 알림과 UI 이벤트로 단축하지 않는다.
60초 누락 복구 주기도 유지하므로 주기적 서버 조회량은 늘리지 않는다.
80ms는 네트워크를 제외한 예약 대기이며 전체 반영 시간 보장이 아니다.
검증: test_live_refresh_scheduler.cjs의 가상 시계로 100개 알림 합치기,
보류 예약 앞당김, 미디어/모달 종료, 이미 잡힌 빠른 예약보다 오류 backoff
우선, 빈 큐 무동작을 확인한다. 실제 Chromium/WebKit 예배·말씀·교회력
테스트로 기존 초안·송출·재생 보호와 반영을 회귀 검증한다.

## 가사 단위 순서 보존 ·2026-10-22

실시간 조회의 ID 정렬은 페이지 조회용이다. 공통 버전 조립 단계에서 저장된
`curated_order`(없으면 `unit_order`) 순으로 정렬한 뒤 normalizeForms를 적용한다.
UUID 정렬을 화면/저장 순서로 사용하지 않는다. 찬송가·CCM·어린이 모두 같은 규칙이다.
동순위는 ID로 안정적으로 정렬하며 DB 가사·사용자 지정 순서·예배 내용은 자동 수정하지 않는다.
회귀 검사는 ID/원본 순서/교정 순서가 서로 다른 3개 가사 단위의 실시간 수신,
재수신 무변경, 후속 저장 준비 순서를 두 브라우저에서 검증한다.

## 찬양 편집 원자 저장 ·2026-10-23

기존 저장에서 발견한 문제: 버전/가사 upsert와 순서 예약, 관련 곡 삭제가
곡 memo CAS보다 먼저 실행되어, 충돌·연결 끊김에도 일부 자료가 변경될 수 있다.
후보는 `get_praise_snapshot_v1` / `save_praise_v1`로 기존 곡 편집 저장을 묶는다.
서버 전체 snapshot CAS와 기존 canonical/worship advisory lock 순서를 공유하고,
기존 테이블 권한/RLS를 유지하는 SECURITY INVOKER 함수로 실행한다.

- 최신본이 편집 시작 기준과 다르면 쓰기를 시작하지 않고 내 입력을 유지한다.
  조회 직후의 경합도 서버 CAS가 막는다. 자동 덮어쓰기·자동 병합 저장은 하지 않는다.
- 가사/버전/순서/곡 메타데이터/관련 곡 변경은 단일 트랜잭션이다.
  오류·취소·권한 거절이면 전체 rollback. 명시한 삭제 ID만 제거한다.
- 결과가 불명확한 요청은 같은 페이지에서 동일 request ID/내용으로 재시도한다.
  곡 memo의 내부 `_praiseCommit` 영수증으로 응답 유실을 확인하며,
  같은 ID에 다른 내용은 거절한다. 전체 페이지 재시작 후 무조건 재전송하지 않는다.
- 저장 중 추가 입력은 mergeEditorDraft로 보존하고 dirty를 유지한다.
  기존 음원/타이밍 및 원본 출처·슬라이드 번호·검토 메모를 가사 저장으로 비우지 않는다.
- 신규 곡 생성/빈 곡 삭제/예배에서의 신규곡 생성은 이번 기존 곡 편집 경로와 별도다.
  기존 버전 삭제 보호와 예배 atomic 경로를 유지한다.

**출시 전 필수:** `migrations/2026-10-23-praise-atomic-save.sql`의 운영 스키마/
권한 호환성 및 함수 적용을 확인한 뒤 앱을 게시한다. 함수 없는 서버로 이 후보 앱을
먼저 배포하면 안전을 위해 찬양 저장을 거절한다. 다중 요청 방식으로 fallback하지 않는다.
열려 있는 구버전 앱은 새 저장 경로를 사용하지 않으므로 운영 전환 시 새로 열어야 한다.
직접 SQL/구버전 클라이언트의 last-write 자체를 이 후보가 금지하는 것은 아니다.
2026-10-23 운영 함수 적용 완료. 6개 테이블 전체 행 해시가 적용 전후 같음을
같은 트랜잭션에서 검증했다. anon/authenticated 실제 권한으로 저장·재시도·
충돌 거절·음원 보존을 검사하고 모든 검증 변경을 rollback했다.
앱 배포는 GitHub gate/Pages 확인 후 별도 기록한다.

검증: `tests/test_praise_atomic.mjs`를 임시 PostgreSQL18.4에서 실행하여
독립 연결 동시 저장, 트랜잭션 중 pg_cancel_backend, RLS 거절 rollback,
오래된 baseline, 응답 유실 replay, 잘못된 재사용, 불완전 계획, 음원 보존을 확인.
`tests/smoke_praise_atomic_save.py`는 Chromium/WebKit 실제 앱 함수에서
조회 실패·송신 전 실패·CAS 경합·응답 유실·추가 입력·재저장을 확인한다.
성구 검증/출력 제목/버전 삭제/미저장 입력 보호 회귀도 별도 확인했다.
이 결과는 운영 서버 적용이나 실제 네트워크 단절 검증을 의미하지 않는다.
