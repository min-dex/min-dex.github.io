# 다른 기기에서 예배 원격 조작

설계안 · 2026-10-20. 아직 구현/DB 적용/배포하지 않았다.
관련 계약: `presenter-control-ideas.md`, `worship-presenter-decisions.md`,
`monitor-operations.md`. 집중 보기의 화면과 기존 presenter/music action을 재사용한다.

## 사용자 흐름

1. 송출 기기에서 예배를 열고 송출을 시작한다. ‘원격 조작’에서 ‘연결 허용’을 누른다.
2. 짧게 유효한 QR 또는 연결 코드를 다른 기기에서 연다. 로그인 후 연결 요청한다.
3. 송출 기기에 요청 기기 이름과 확인 코드가 뜬다. ‘보기만 허용’ 또는 ‘조작 허용’을 고른다.
4. 원격 화면에 예배명, 송출 기기, 연결 상태와 현재/다음 화면을 표시한다.
5. 송출 기기에서 언제든 권한 회수/전체 연결 종료한다. 송출 종료·예배 변경 시 세션도 끝낸다.

QR/코드는 연결 요청 수단이며 조작 권한 자체가 아니다. 이름이 같은 기기는 확인
코드로 구분한다. 원격 시작 버튼을 기존 읽기 전용 ‘기기 상태’ 버튼에 합치지 않는다.
로그인 없이 열리는 현재 예배 읽기 권한과 원격 조작 권한을 구분한다.

## 화면

송출 기기: 원격 조작 → 연결 허용 / 요청 목록 / 연결된 기기 / 전체 종료.
조작 권한은 동시에 한 기기에만 부여한다. 다른 기기로 넘길 때 기존 권한을 회수한다.
송출 기기의 직접 조작은 항상 가능하며 원격 요청보다 우선한다.

원격 화면은 별도 경로의 간결한 조작 화면이다. 현행 편집 화면의 고정 사이드바
계약을 바꾸지 않는다. 큰 화면은 현재/다음을 나란히, 좁은 화면은 현재를 위에 둔다.
아래는 이전/다음, 음원 상태와 재생/일시정지·정지·자동 넘김 복귀, 가로 슬라이드 목록.
터치 버튼은 최소 44px. 색만으로 연결/승인/오류 상태를 구분하지 않는다.
원격에는 편집 입력창과 저장 버튼이 없고 현장 음원을 원격에서 재생하지 않는다.

| 상태 | 화면과 조작 |
| --- | --- |
| 승인 대기 | 요청한 기기/예배 표시, 조작 비활성 |
| 보기 전용 | 현재/다음 상태 확인, 조작 버튼 숨김 |
| 조작 가능 | 현재 수신 상태 기준으로 버튼 활성 |
| 처리 중 | 요청한 버튼 잠금, 호스트 실행 확인 뒤 상태 갱신 |
| 응답 지연/끊김 | 마지막 확인 시각, 조작 비활성, 재연결 |
| 권한 회수/세션 종료 | 명확한 종료 이유, 다시 연결 요청 |

첫 범위: 이전/다음, 특정 장 선택 후 명시적 ‘이 장 송출’, 음원 재생/일시정지/정지,
자동 넘김 복귀. 썸네일 한 번 누르기는 원격 미리보기 선택이며 즉시 송출하지 않는다.
원격에서 송출 시작/종료·전체화면·모니터 선택·DB 편집·장비 제어는 제공하지 않는다.
이 범위에서는 원격 암전도 제외하고 현장의 기존 암전 버튼을 유지한다.

## 실행 책임과 명령 계약

송출 창을 가진 제어 탭 하나가 host다. 서버 세션에 host instance와 epoch를 고정한다.
다른 탭은 이를 승계하지 않는다. 새로고침/host 교체/예배 전환 시 새 epoch와 재승인이 필요하다.
서버는 한 교회·송출 대상에 하나의 유효한 host lease만 허용한다.

원격은 의도를 전송하고, host가 기존 presenter action 및 runServiceMusicAction을
호출한다. 기존 음원 소유자·songTimingEligible·암전·실시간 말씀·자동 넘김 조건을
모두 재검사한다. 음원 seek, 파일 URL 실행, 임의 JavaScript와 임의 action명은 허용하지 않는다.

명령 필드: sessionId, epoch, commandId(UUID), controllerId, sequence,
serviceId, expectedRevision, action, targetSlideId 또는 sourceKey/groupId.
서버가 issuedAt/expiresAt(초기 제안 2초)을 부여한다. 클라이언트 시각을 신뢰하지 않는다.
허용된 action별 payload schema와 크기를 제한하고 기기·세션별 요청률을 제한한다.

1. 서버가 로그인·교회 운영 권한·세션·기기 grant·lease·기한을 검증해 명령을 접수한다.
2. private channel은 해당 host에게 명령 ID가 준비됐음을 알린다.
3. host는 서버 claim RPC로 명령을 한 번만 확보한다. RPC가 권한/기한/epoch를 다시 검사한다.
4. host는 현재 revision/예배/음원 소유자와 대조한다. 불일치하면 실행하지 않고 최신 상태를 보낸다.
5. 동기적인 기존 조작 진입점에 전달하고 처리 결과와 새 revision을 원격으로 응답한다.

로컬 조작도 revision을 올린다. 원격은 한 번에 하나의 명령만 보낸다. 재생·일시정지는
명시적 목표 상태로 변환하고, 늦은 toggle을 다시 실행하지 않는다. 동일 commandId는
재실행하지 않고 기존 결과만 반환한다. 수신 확인과 실제 실행 완료를 구분한다.
claim 이후 host가 죽으면 결과는 ‘실행 여부 확인 불가’다. exactly-once 실행을 주장하지
않으며 자동 재전송하지 않는다. 재접속 뒤 현재 상태를 보고 사용자가 다시 조작한다.
종료/회수는 host 메모리에서 즉시 차단하고 서버에서도 grant를 취소한다.

## 서버와 전송

구현 권고: Supabase의 기존 로그인에 교회별 remote operator 권한을 서버에서 검증하고,
private Realtime Broadcast를 상태/알림 전송에 사용한다. 기존 공개 기기 현황 RPC와
공용 데이터 변경 채널은 조작 권한 증거로 재사용하지 않는다.

새 서버 모델 제안: remote_sessions(host, epoch, service, expiry/lease),
remote_requests(만료되는 요청), remote_grants(view/control/revoked),
remote_commands(짧은 유효기간·claim·결과, 재생 대기열이 아닌 중복 방지 기록).
토큰은 해시만 서버 저장하고 URL query에 조작 토큰을 싣지 않는다. QR 요청 nonce는
1회·2분 만료로 시작하고 코드 대입 시도를 제한한다. 초안/가사/음원 파일을 복제하지 않는다.
세션/권한은 서버가 원본이고 브라우저 메모리는 유효 연결의 임시 상태만 가진다.

RLS/서버 함수에서 사용자·교회·세션·대상별 읽기/쓰기 권한을 제한한다. 로그인만으로
교회 운영 권한을 부여하지 않는다. 실제 운영자 식별/회원 모델은 구현 전에 기존 DB와
대조해야 하며, 확인되지 않은 상태에서는 public channel로 대체하지 않는다.
공용 Realtime 전체 설정을 무작정 바꾸면 기존 동기화가 끊길 수 있으므로 원격 채널의
접근 정책과 기존 공개 채널의 영향을 별도 staging에서 검증한다.

공식 근거: [Realtime authorization](https://supabase.com/docs/guides/realtime/authorization),
[Broadcast](https://supabase.com/docs/guides/realtime/broadcast).
private channel의 접근 정책만으로 명령별 즉시 회수/실행 확인까지 해결된다고 보지 않는다.
위 claim/실행 응답은 민덱스가 구현할 별도 계약이다.

## 끊김·성능

host heartbeat 제안: 5초, lease 15초. 연결 상태가 불확실하면 원격 입력을 잠근다.
앱이 배경으로 가거나 브라우저가 절전하면 신뢰 가능한 새 snapshot을 받은 뒤만 재활성화한다.
연결이 끊겨도 host의 송출·음원·자동 넘김은 계속된다. 오프라인 명령을 저장/재생하지 않는다.

장 전환/재생 상태 변화는 즉시 작은 snapshot을 보내고, 재생 위치는 최대 초당 1회 전송한다.
전체 화면 이미지·동영상·음원 스트리밍은 하지 않는다. 현재/다음 slide model만 보내며
표시할 수 없는 로컬 미디어는 ‘현장 기기에서 재생 중’으로 표시한다.
승인된 세션에만 필요한 현재/다음 텍스트를 보내고 모든 예배 DB를 내려주지 않는다.
유휴 polling은 추가하지 않는다. 재연결 시 현재 snapshot 하나로 맞추고 명령 기록을 재생하지 않는다.
목표 반응시간은 같은 네트워크 p95 300ms, 외부 네트워크 p95 800ms로 측정하되 보장값은 아니다.
성능 목표를 못 맞추면 정확성/권한 검사를 생략하지 않고 단계별 지연을 먼저 측정한다.

## 구현 순서와 완료 기준

1. 네트워크 없는 모의 host/controller로 화면·상태 머신·기존 action adapter를 검증한다.
2. 운영자 권한 모델 확인 후 staging에 세션/RLS/RPC/private channel을 구현한다.
3. 두 브라우저 + 실제 휴대폰에서 승인/회수/전환/지연/재접속을 검사한다.
4. 현장 송출·음원 보존 검증 후 별도 기능으로 배포한다.

필수 실패 테스트: 타 교회/미승인 기기/만료 코드/위조 host/잘못된 action 거부,
중복·순서 뒤바뀜·2초 초과 명령 미실행, 로컬 조작과 원격 경합, 같은 이름의 기기,
host 탭 종료·절전·epoch 변경, claim 후 crash, 회수 직후 요청, 원격 연타,
음원 소유 예배 변경, 자동 넘김 해제/복귀, 지연 중 UI가 실행 완료로 오표시하지 않음.
실제 DB 권한과 기기 연동 검증 전에는 원격 구현 완료로 표시하지 않는다.
